# GovAssist — AI Assistant for Navigating Public Services (RAG over Official Documents)

**M.Sc. thesis project plan — end-to-end**
Author: Mashkhurbek Mashrabov · ITPU / EPAM Masters · Software Engineering (AI Engineering focus)
Working title: *"Design and evaluation of a retrieval-augmented AI assistant for citizen access to public services in the Uzbek language"*

> This document is written to be executed by AI coding agents (Claude Code, Cursor, etc.) phase by phase.
> Each phase has explicit deliverables and acceptance criteria. Agents must not skip a phase's acceptance checks.
> **Rule for agents:** never fabricate evaluation data, user-study results, or benchmark numbers. All results must come from actual runs and be logged to `docs/results/`.

---

## 0. One-paragraph summary

A citizen types (or speaks) a question such as *"Pasportni qanday almashtiraman?"* in Uzbek (Latin or Cyrillic) or Russian, and gets a grounded, step-by-step answer: required documents, fees, deadlines, where to apply, and links to the source articles. Answers are generated by an LLM strictly from a curated corpus of official documents (laws, decrees, service descriptions) retrieved via vector search. The system is a **Django backend + PostgreSQL/pgvector + LLM API**, exposed through a **mobile app**. The thesis evaluates answer accuracy, groundedness (hallucination rate), retrieval quality across Uzbek scripts, and usefulness to non-technical users, compared against a plain LLM without retrieval.

## 1. Goals, non-goals, constraints

### Goals
1. Working end-to-end system: ingestion → retrieval → grounded answer → mobile UI.
2. Measurable research contribution: RAG vs. no-RAG accuracy and hallucination rate on a hand-built Uzbek/Russian question set; effect of Latin/Cyrillic normalisation on retrieval.
3. Usable by a non-technical citizen: one text box, plain-language answers, source links, feedback buttons.

### Non-goals (explicitly out of scope — keep the project "not hard")
- No model fine-tuning. LLM and embedding models are used as-is via API or off-the-shelf weights.
- No transactional actions (no submitting applications, no logins to government systems).
- No legal advice claims — every answer carries a disclaimer and source links.
- No multi-tenant / multi-organisation platform. One national corpus.
- Voice is optional (Phase 8, only if time allows).

### Constraints
- Backend: Python 3.12, Django 5 + DRF. No FastAPI, no Node backend.
- Storage: PostgreSQL 16 with `pgvector` (no separate vector DB — fewer moving parts).
- Async work: Celery + Redis.
- LLM: any OpenAI-compatible chat API (configurable base URL + model). Must be swappable via env vars. Default assumption: a hosted model with good Russian/Uzbek support; fallback: local model via Ollama for offline demo.
- Embeddings: multilingual model (`intfloat/multilingual-e5-base` or `BAAI/bge-m3`) served locally by a small embedding service or via `sentence-transformers` in a Celery worker.
- Mobile: Flutter (single codebase, Android first; iOS if a Mac is available). Alternative: React Native. Do not build a web SPA as the primary UI.
- Everything runs with one `docker compose up`.
- Languages: Uzbek Latin, Uzbek Cyrillic, Russian. UI in Uzbek Latin by default.
- Licensing: use only publicly published official documents; record source URL, publication date, and licence/terms for every document.

## 2. Architecture

```
┌──────────────┐   HTTPS/JSON    ┌──────────────────────────────────────┐
│  Flutter app │ ─────────────▶  │  Django + DRF (API)                  │
│  (Android)   │ ◀───────────── │  /api/v1/chat, /sessions, /feedback  │
└──────────────┘                 └───────────────┬──────────────────────┘
                                                 │
                    ┌────────────────────────────┼──────────────────────┐
                    ▼                            ▼                      ▼
          ┌──────────────────┐        ┌────────────────────┐   ┌────────────────┐
          │ PostgreSQL 16    │        │ Celery workers     │   │ LLM API        │
          │ + pgvector       │        │ (Redis broker)     │   │ (OpenAI-compat)│
          │ docs, chunks,    │        │ - ingestion        │   └────────────────┘
          │ embeddings,      │        │ - embedding        │
          │ sessions, logs   │        │ - eval runs        │   ┌────────────────┐
          └──────────────────┘        └────────────────────┘   │ Embedding svc  │
                                                               │ (e5 / bge-m3)  │
                                                               └────────────────┘
```

### Request flow (`POST /api/v1/chat`)
1. Normalise query: detect script (Latin/Cyrillic/Russian), transliterate Uzbek Cyrillic → Latin for retrieval (keep original for display).
2. Embed query → `pgvector` cosine search (top-k=8) + optional BM25/`tsvector` keyword search → merge (reciprocal rank fusion) → top-5 chunks.
3. Build prompt: system instructions (answer only from context, cite chunk IDs, say "I don't know" if not covered, answer in the user's language), retrieved chunks, conversation history (last 4 turns).
4. Call LLM (streaming). Parse citations `[doc:ID]` → resolve to document titles + URLs.
5. Store turn, retrieved chunk IDs, latency, token counts. Return answer + sources.

### Data model (Django apps)
- `corpus`: `Source`(name, url, publisher, licence), `Document`(source, title, doc_type, published_at, canonical_url, raw_text, language), `Chunk`(document, order, text, text_latin, embedding vector(768/1024), token_count)
- `chat`: `Session`(anon device id, language), `Message`(session, role, content, retrieved_chunks M2M, latency_ms, prompt_tokens, completion_tokens, model)
- `feedback`: `Feedback`(message, rating 👍/👎, comment)
- `eval`: `EvalQuestion`(question, language, script, expected_answer, expected_doc_ids), `EvalRun`(config json, started_at), `EvalResult`(run, question, answer, retrieved_ids, scores json)

## 4. Phased plan

Each phase ≈ 1–2 weeks of part-time work. Total ≈ 14–18 weeks for Phases 1–7. Phase 8 is optional.

### Phase 0 — Project setup (2–3 days)
**Tasks**
- Init monorepo, `docker-compose.yml` with `postgres:16` (+ `pgvector` extension), `redis`, `backend`, `worker`, `embedding-service`.
- Django project with split settings, DRF, `django-environ`, `pgvector` Django package, Celery wired to Redis.
- Pre-commit: `ruff`, `black`, `mypy` (lenient). GitHub Actions: lint + pytest.
- Health endpoint `/api/v1/health` reports DB, Redis, embedding service, LLM reachability.

**Acceptance**
- `docker compose up` → health returns all green.
- CI passes on an empty test.

### Phase 1 — Corpus acquisition (1–2 weeks)
**Tasks**
- Choose 3–5 high-value service domains for the pilot (suggested: passport/ID, birth/marriage registration, driving licence, business registration, utilities/subsidies). Keep the corpus small and clean: ~100–300 documents.
- Candidate sources: `lex.uz` (laws, decrees — check terms of use), `my.gov.uz` service pages, ministry FAQ pages. Prefer HTML; fall back to PDF text extraction (`pdfplumber`).
- Write `scripts/ingest_*.py`: fetch → clean → store `Document` with full metadata. Respect robots.txt and rate limits; cache raw HTML on disk.
- Record every source in `docs/corpus-sources.md`.

**Acceptance**
- ≥ 100 documents in DB with title, URL, publication date, language, and raw text.
- No document without a resolvable source URL.

### Phase 2 — Chunking, normalisation, embeddings (1 week)
**Tasks**
- Chunker: split by article/section headings first, then by ~400–600 tokens with 80-token overlap. Keep heading path as chunk prefix ("Law X › Chapter 2 › Article 14").
- Uzbek script normalisation module: Cyrillic → Latin transliteration (handle ў→oʻ, ғ→gʻ, ҳ→h, ъ→ʼ; apostrophe variants ʻ ʼ ' ` → single canonical form). Store both `text` and `text_latin`.
- Celery task `embed_chunks` batching 64 chunks per call to the embedding service; write vectors to `Chunk.embedding`. Create HNSW index (`vector_cosine_ops`).
- Management command `rebuild_index`.

**Acceptance**
- 100% of chunks embedded; HNSW index present.
- Unit tests for transliteration on a 50-word golden list.
- Ad-hoc search for 10 known questions returns the correct document in top-5 for ≥ 8/10.

### Phase 3 — Retrieval service (1 week)
**Tasks**
- `retrieval.search(query, lang, k)`: embed normalised query → cosine top-k; parallel `tsvector` (Postgres FTS, `simple` config on `text_latin`) top-k; merge via reciprocal rank fusion.
- Optional reranker hook (`bge-reranker-base`) behind a feature flag — off by default.
- Return chunks with document metadata and scores.
- Log every retrieval (query, ids, scores) for later analysis.

**Acceptance**
- Retrieval unit tests with a fixture corpus.
- p95 retrieval latency < 300 ms on the pilot corpus (measured, logged in `docs/results/`).

### Phase 4 — Answer generation (1–2 weeks)
**Tasks**
- LLM client: OpenAI-compatible, streaming, timeout, retry with backoff, token accounting. Model/base URL/key from env.
- Prompt builder (versioned files in `docs/prompts/vN.md`):
  - Answer only from provided context; if insufficient → say so and suggest the nearest relevant service.
  - Cite as `[doc:<id>]` after each factual statement.
  - Answer in the user's language and script; use short numbered steps; list documents, fees, deadlines, and where to apply.
  - Mandatory footer: "This is informational, not legal advice; verify with the official source."
- Citation parser → `sources[]` with title, article/section, URL.
- Conversation memory: last 4 turns, condensed if over budget.
- Guardrails: refuse off-topic requests politely; strip PII from logs (regex for passport series, phone numbers, PINFL).

**Acceptance**
- `POST /api/v1/chat` streams an answer with ≥ 1 valid citation for in-corpus questions.
- Manual check of 20 questions: answer language matches query language 20/20.

### Phase 5 — Public API + mobile app (2–3 weeks)
**Backend tasks**
- Endpoints: `POST /sessions`, `POST /chat` (SSE streaming), `GET /sessions/{id}/messages`, `POST /feedback`, `GET /services` (browse the covered service catalogue).
- Anonymous device-token auth (no accounts). Rate limiting (`django-ratelimit`). OpenAPI schema via `drf-spectacular`.

**Mobile tasks (Flutter)**
- Screens: Onboarding/language pick → Chat (streaming bubbles, source chips that open the official URL) → Service catalogue (browse by domain, tap a suggested question) → History → Settings (language, clear data).
- Offline-safe: show cached history, clear error state when backend unreachable.
- Accessibility: large text support, high-contrast, simple wording. Target users are non-technical.
- Optional: speech-to-text via the platform's built-in recogniser (`speech_to_text` package) — cheap win for low-literacy users.

**Acceptance**
- APK installs on a physical Android device; a first-time user can ask a question and open a source link within 60 seconds with no instructions.
- API documented at `/api/schema/swagger-ui/`.

### Phase 6 — Evaluation (thesis core, 2–3 weeks)
**Build the evaluation set (no shortcuts)**
- 150 questions total: 50 Uzbek Latin, 50 Uzbek Cyrillic (same 50 questions transliterated), 50 Russian. Written by the author, reviewed by 1–2 native speakers. For each: expected key facts (documents, fee, deadline, authority) and expected source document IDs. Include 20 out-of-corpus questions to test refusal.
- Store as `eval/fixtures/questions_v1.jsonl`. Version it.

**Metrics**
- Retrieval: Recall@5, MRR against expected doc IDs. Compare: (a) vector only, (b) keyword only, (c) hybrid RRF; and with/without Cyrillic→Latin normalisation.
- Answer quality: LLM-as-judge (a *different* model than the generator) scoring correctness (0–2) and groundedness (each claim supported by a cited chunk: yes/no) + a manual check on a 30-question random sample to validate the judge (report agreement).
- Hallucination rate: % of answers with ≥ 1 unsupported factual claim.
- Refusal accuracy on out-of-corpus questions.
- Baselines: (1) same LLM, no retrieval; (2) retrieval with no citation instruction.
- System: p50/p95 end-to-end latency, tokens/cost per answer.

**User study (qualitative, small)**
- 8–12 non-technical participants, 5 tasks each (e.g. "find out what you need to replace a lost passport"). Measure task success, time, SUS score, and 3 open questions. Ethics: informed consent, no personal data stored.

**Acceptance**
- `scripts/run_eval.py --config X` writes a timestamped JSON + Markdown table to `docs/results/`. Results are reproducible from a fixed corpus snapshot and fixed prompt version.
- All tables in the thesis are generated from files in `docs/results/`.

### Phase 7 — Hardening, deployment, thesis writing (2–3 weeks)
- Deploy backend on a single VPS (Docker Compose, nginx + TLS, Postgres backups). Observability: structured JSON logs, request IDs, basic Prometheus metrics (optional).
- Cost control: response cache keyed on normalised query + corpus version.
- Write the dissertation: intro/problem, related work (RAG, low-resource languages, e-government chatbots), system design, evaluation, results, threats to validity, future work.
- Prepare a 10-minute demo script and a 12–15 slide deck.

### Phase 8 (optional) — Voice channel
- Only if Phases 1–7 are done. Add Telegram bot or on-device STT/TTS in the app. Do **not** start SIP/telephony in this thesis.

## 5. Research framing (for the proposal / advisor)

**Problem.** Citizens struggle to find accurate, actionable information about public services scattered across legal texts and portals, especially in Uzbek, a low-resource language with two scripts.

**Research questions**
- RQ1: How accurately and how grounded are answers from a RAG assistant over official Uzbek/Russian documents compared with a plain LLM?
- RQ2: What is the effect of Uzbek Cyrillic→Latin normalisation and hybrid (vector + keyword) retrieval on retrieval quality?
- RQ3: Can non-technical users complete typical public-service information tasks with the assistant, and how do they rate it?

**Method.** Design science / mixed methods: build the artefact (Phases 0–5), quantitative evaluation on a curated question set (Phase 6), small qualitative user study.

**Expected contribution.** An open, reproducible RAG pipeline and evaluation set for Uzbek public-service documents; empirical evidence on script normalisation and hybrid retrieval for Uzbek; a usable citizen-facing mobile assistant.

## 7. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Uzbek embedding quality is poor | Hybrid keyword search + transliteration; measure and report honestly; try `bge-m3` vs `e5` |
| Legal texts change; corpus goes stale | Store `fetched_at` and corpus version; show source date in the UI; re-ingest command |
| LLM hallucinates fees/deadlines | Strict citation prompt; groundedness metric; "verify with source" footer |
| Scraping restrictions | Prefer official APIs/downloads; document terms; keep corpus small and public |
| Scope creep (voice, accounts, transactions) | Non-goals section is binding; Phase 8 only after Phase 7 |
| Advisor expertise mismatch | Frame Phase 7 deployment/observability and latency evaluation as the distributed-systems angle |
